# BillDesk API Documentation Mapping

## Official API Endpoints (From Screenshots)

### 1. Create Order ✅ IMPLEMENTED
**Endpoint**: `POST /payments/ve1_2/orders/create`
**Status**: Fully implemented in `billdesk.ts`

**Required Fields** (from docs):
- `orderid` - Unique ID generated by merchant ✅
- `mercid` - Merchant ID (KANAKV2) ✅
- `order_date` - Format: YYYY-MM-DDThh:mm:ssTZD ✅
- `amount` - Two decimals (e.g., 299.28) ✅
- `currency` - 356 for INR ✅
- `ru` - Redirect URL after transaction ✅
- `itemcode` - Item code (DIRECT recommended) ✅

**Returns**:
- `bdorderid` - Generated by BillDesk ✅
- `rdata` - Generated by BillDesk (format: hex_string.encoded_suffix) ✅
- `payment_link` - Direct payment link ✅

### 4. Create Transaction ✅ IMPLEMENTED
**Endpoint**: `POST /payments/ve1_2/transactions/create`
**Status**: Fully implemented in `billdesk.ts`

**Required Fields** (from docs):
- `mercid` - Merchant ID ✅
- `orderid` - Order ID ✅
- `amount` - Two decimals ✅
- `bankid` - For UPI/Netbanking (optional) ✅
- `currency` - 356 for INR ✅
- `ru` - Redirect URL ✅
- `authentication_type` - "3ds2" recommended ✅
- Device info (init_channel, ip, user_agent, etc.) ✅

**Returns**:
- `transactionid` - Generated by BillDesk ✅
- `auth_status` - "0300" (success), "0002" (pending), "0399" (failed) ✅
- `next_step` - "3ds2_challenge", "capture_otp", "3ds2_frictionless", "redirect" ✅
- `redirect_url` - For redirects ✅
- `challenge_data` - For 3DS2 ✅

---

### 5. Update Transaction ✅ IMPLEMENTED
**Endpoint**: `POST /payments/ve1_2/transactions/update`
**Status**: Fully implemented in `billdesk.ts`

**Required Fields** (from docs):
- `mercid` - Merchant ID ✅
- `transactionid` - From Create Transaction ✅
- `response_parameters` - Object with flow-specific data ✅
- `payment_method_type` - card, netbanking, upi, eft, cardless, bankaccount ✅

**Response Parameters by Flow**:
- **3DS2 Flow**: Send `cres` (JWT from ACS) ✅
- **OTP Flow**: Send `otp` (6-digit code) ✅
- **Other**: Follow specific flow requirements ✅

**Returns**:
- `auth_status` - "0300" (success) ✅
- `authcode` - Authorization code ✅
- `bank_ref_no` - Bank reference number ✅
- `rrn` - RRN number ✅

---

### 6. Retrieve Transaction ✅ IMPLEMENTED (UPDATED)
**Endpoint**: `POST /payments/ve1_2/transactions/retrieve`
**Status**: Recently added to `billdesk.ts`
**Purpose**: Query existing transaction by transactionid or orderid

**Request Parameters**:
- `mercid` - Merchant ID
- `transactionid` - (Optional) BillDesk transaction ID
- `orderid` - (Optional) Merchant order ID
- `refund_details` - (Optional) Boolean to get refund info

**Returns**:
- `transactionid`
- `orderid`
- `auth_status` - Current authorization status
- `settlement_status` - Settlement status
- `authcode` - If authorized
- `bank_ref_no` - Bank reference
- `rrn` - RRN
- `amount`
- Optional: `refund_details` array if refund_details=true

**Use Cases**:
- Poll transaction status (frontend polling)
- Verify transaction before settlement
- Get refund information
- Reconciliation

### 7. Create Mandate (NEW - For Subscriptions)
**Endpoint**: `POST /u2/pgsi/ve1_2/mandates/create`
**Purpose**: Create subscription/mandate for recurring payments
**Status**: Optional - skip for one-time payments

**Required Fields**:
- `mercid`
- `customer_refid` - Unique customer reference
- `subscription_refid` - Unique subscription reference
- `subscription_desc` - Customer friendly description
- `currency` - 356
- `frequency` - week, month, etc.

**Notes**: "A mandate can be created by providing details of the subscription and the associated payment method."

## Key Takeaways from API Docs

1. **BD-Traceid is mandatory** - For idempotency (prevent duplicate charges)
2. **BD-Timestamp format** - YYYY-MM-DDThh:mm:ssTZD (ISO 8601)
3. **Amount format** - Always string with 2 decimals
4. **Currency** - "356" for INR (ISO code)
5. **Authentication** - 3ds2 recommended (from docs screenshot)
6. **Device info required** - For 3DS2 challenge
7. **next_step values** - Guide customer experience flow
8. **Retrieve endpoint** - For status polling (better than webhooks for reliability)

## Webhook Implementation Decision

**Since webhooks are NOT documented:**

✅ **Use our auto-detect strategy**:
1. Deploy webhook endpoint
2. First transaction sends webhook
3. We auto-detect signature header & algorithm
4. Log which method worked
5. Confirm with BillDesk

✅ **Alternative: Use Retrieve Transaction for polling**:
- Call `/payments/ve1_2/transactions/retrieve` every 2 seconds
- Check `auth_status` = "0300" for success
- Reliable (no webhook delivery issues)
- May have slight delay in settlement status

**Recommended**: Use BOTH:
1. Frontend polls with Retrieve Transaction (instant feedback)
2. Webhook for backend settlement confirmation (async)
